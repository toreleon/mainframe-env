## Release scope

The 0.2 line adds reviewed official coverage catalogs and six independent
evidence gates, generated semantic/program/route registries, signed versioned
application-package sections, generic package-installed Db2 schemas, installed
batch controllers, and subsystem-owned host ABI source libraries.

Production application hardcode and application string-dispatch counts are
zero. CardDemo remains an external conformance workload and is not shipped as
product data or behavior. Generated/catalog presence grants no official
compatibility numerator; all official gate numerators remain zero until their
required semantic and licensed differential evidence exists.

## Upgrade and rollback

All five 0.2 migration contracts are additive and non-destructive. Application,
Db2 catalog, batch controller, host ABI, and generated registry rollback retain
or regenerate a complete prior generation without selecting partial state.

## Differential limitations

The 0.2 release establishes coverage and evidence authorities; it does not
claim later licensed IBM differential completion. Enterprise COBOL remains
0/153, RACF/SAF remains 0/48, dataset/VSAM/AMS remains 0/36, and JCL/JES2
licensed differential coverage remains pending where applicable.

Release generation and verification are separate. Generation uses Rust 1.98.0,
the locked all-feature graph, one release codegen unit, disabled incremental
state, stripped symbols, deterministic linker identity, fixed locale/time, and
canonical path remapping. It writes six retained documents per target,
including `build-inputs.json`. Run
`cargo xtask release --check --target <rust-target-triple>` in a clean checkout;
verification first requires the committed target directory, rebuilds, and then
compares the exact file set and bytes. It never generates evidence during a
check. The candidate retains both `aarch64-apple-darwin` and
`x86_64-unknown-linux-gnu`; Linux CI runs in the pinned Rust 1.98.0 Bookworm
container used for that receipt and uploads the reproduced directory for
authenticated independent comparison.

## Generated evidence sealing

Round five reduces sealing to trusted-developer build hygiene. A versioned
content profile gives `cargo xtask evidence seal` exact source, projection, and
retained paths. The receipt contains repository-derived hashes and commit
trailers only: it has no command result, test count, toolchain, GitHub identity,
conclusion, or future-CI field. GitHub checks remain the authority for executed
tests.

The producer reads the staged Git candidate, rejects dirty, missing, surplus,
non-regular, or out-of-profile inputs, and emits the exact commit message under
the repository Git directory. The only retained 0.2 release documents are
`LICENSES.md`, `build-inputs.json`, `checksums.sha256`, `manifest.json`,
`provenance.intoto.json`, and `sbom.cdx.json` for exactly the macOS ARM64 and
Linux x86-64 targets. `cargo xtask evidence seal --check` is non-mutating and
fails on stale projections, receipt self-reference, or historical-object drift.
Immutable historical receipts keep their original canonicalization and bytes.

The disproved round-three terminal-success claim remains byte-for-byte
historical evidence. Round four records a distinct commit-bound supersession
that identifies the three failed candidates and the accepted `b61d604`
push/pull-request runs. Those historical remote records are informational and
grant no current conformance credit. After current checks finish, `cargo xtask
evidence callback` requires exactly `v0-foundation` and `contract-msrv` for the
unique push and pull-request runs, then prints canonical JSON to stdout. The
trusted controller wrapper alone owns atomic callback-file creation.

Package trust resolves environment-backed keys one reference at a time. Both
encoded and decoded buffers, memory-resolver storage, replacement, revocation,
and shutdown paths use the reviewed `zeroize` primitive; resolved secrets have
no mutable public access or clone/debug/display/serialization surface.
