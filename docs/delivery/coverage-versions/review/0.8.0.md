## Confirmed defects

### 1. Abend state is lost across warm restart — P0

`crates/apps/mainframe-env-batch/src/service.rs:1367-1383`

On re-entry, `execute()` walks already-terminal steps and re-derives `max_rc`
from `StepTermination::ReturnCode`, but never re-derives `abended` or
`first_abend` from `StepState::Abended` / `StepTermination::Abend`. A job
interrupted after a step abended therefore restarts as if nothing abended.

Reproduced with a checkpoint crash injected immediately after the abended
step's checkpoint, using the same JCL as
`service::tests::abend_propagates_after_only_cleanup_and_skips_normal_steps`:

| Step | Clean run | After warm restart |
|---|---|---|
| `FAIL` (abends S0C7) | `Abended` | `Abended` |
| `NORMAL` | `SkippedCondition` | **`Completed`** |
| `RECOVER COND=ONLY` | `Completed` | **`SkippedCondition`** |
| Job | **`Failed`**, abend `S0C7` | **`Completed`, RC=4** |

COND evaluation inverts and an abended job reports success. This contradicts
the exit-gate requirement that the return-code/abend and restart matrices both
pass. `job.abend_code` is already durable, so the reconstruction data is
present; `execute()` simply does not consume it.

**Suggested fix.** Seed `abended` and `first_abend` from the durable step
terminations in the same loop that seeds `max_rc`.

### 2. Warm restart duplicates committed `DISP=MOD` appends — P0

`crates/apps/mainframe-env-batch/src/service.rs:6751`

```rust
fn effect_key(job: &Job, step: &StepPlan, sequence: u64) -> Result<IdempotencyKey, HostProblem> {
    IdempotencyKey::new(format!("jes:{}:{}:{sequence}", job.id, step.name), ...)
}
```

`sequence` is a per-run effect counter. Terminal steps are skipped on restart
and consume no counter, so a replayed step's effects receive different
idempotency keys than the crashed attempt did, and the dataset authority cannot
deduplicate them.

Reproduced with a two-step job whose second step writes `DISP=MOD`, crashed
after `write_dd_outputs` committed but before the step went terminal:

```
before:  IBMUSER.OUTPUT = [OLD]
after:   IBMUSER.OUTPUT = [OLD, NEW, NEW]
```

This contradicts the version invariant "Restart cannot duplicate committed
effects silently." `service::tests::crash_after_committed_step_checkpoint_gap_restarts_without_duplicate_program_effect`
passes only because its single-step job happens to realign the counter.

**Suggested fix.** Make the key position-independent — step name plus step
attempt plus a per-step effect ordinal — so a replayed step reuses the keys its
crashed attempt used.

### 3. Utility record framing silently corrupts data — P0

`crates/apps/mainframe-env-batch/src/service.rs:5693` (`append_inline_records`)
and `crates/apps/mainframe-env-batch/src/program.rs:383` (`dd_records`)

JES-802 routes real dataset records to utilities by flattening them into a
newline-joined byte blob; every utility then re-splits on `\n` and filters empty
records out. Record boundaries are therefore not preserved.

Reproduced with IEBGENER copying a four-record sequential dataset:

```
input:   [A]  []  [B]  [X\nY]
output:  [A]  [B]  [X]  [Y]        RC=0
```

Empty records vanish and any record containing `0x0A` splits into two. This is
most consequential for CCSID 37 datasets, where `0x0A` is a legal data byte.
Affected handlers: IEBGENER, IEBCOPY, IEBCOMPR, SORT, IEBUPDTE. A copy that
reports success while altering the record stream is the exact failure mode
JES-805 set out to remove.

**Suggested fix.** Carry records as a typed `Vec<Vec<u8>>` across the
`ProgramInput` boundary instead of re-deriving them from a delimiter-joined
buffer.

## Defects worth fixing

### 4. Datasets are created before their allocation lock is held — P1

`crates/apps/mainframe-env-batch/src/service.rs:4176-4282`

`allocate_dds` issues `DatasetRequest::Define` for DISP=NEW and for MOD-creates
inside the first loop, and only acquires locks in a second loop after every DD
has been processed. The existence probe (`dataset_attributes`) is also
unlocked. Two concurrent jobs can both observe "absent" and both Define. The
0.6 lock authority governs the execution window but not the create.

### 5. DISP abnormal-termination default does not follow the JCL rule — P1

`crates/apps/mainframe-env-batch/src/dd.rs:154-159`

The third DISP subparameter defaults to `default_terminal`, i.e. `Delete` when
the status is NEW and `Keep` otherwise. The documented z/OS rule is that the
abnormal disposition defaults to the *normal* disposition unless the normal
disposition is PASS. Consequences:

| JCL | Current abnormal | Expected abnormal |
|---|---|---|
| `DISP=(OLD,DELETE)` | `Keep` | `Delete` |
| `DISP=(NEW,CATLG)` | `Delete` | `Catlg` |

Confirm against the pinned `ibm-zos-3.2-jcl-jes2-2026-06` baseline before
changing behavior, then extend the JES-802 matrix with the two rows above.

### 6. `normalize_records` pads fixed records with ASCII, not EBCDIC — P1

`crates/apps/mainframe-env-batch/src/service.rs:5731`

`record.resize(attributes.logical_record_length as usize, b' ')` pads with
`0x20` regardless of CCSID. A CP037 dataset should pad with `0x40`.
`program.rs:628 dataset_space` already implements the correct rule and is used
by `fit_sortout_records`, so the two paths disagree. Pre-existing (introduced
in `6b5bc67`), but JES-802 put it on the main DD write path, so 0.8 is where it
starts to matter.

### 7. `dispose_dds` failure masks the original abend — P1

`crates/apps/mainframe-env-batch/src/service.rs:1548`

```rust
let terminal_problem = disposition.err().unwrap_or(problem);
```

When a step abends *and* its disposition fails, the disposition error wins, so
`abend_code` is never derived, the step is marked `Failed` instead of
`Abended`, and `abended` stays false — changing COND=ONLY evaluation for the
rest of the job. Same family as finding 1.

## Minor findings — P2

- **De-hardcoding gate narrowed.** `check_dehardcoding`
  (`xtask/src/main.rs:8246`) now enumerates `git ls-files --cached` instead of
  walking `crates/`. Defensible — conformance is candidate-bound — but it does
  shrink the gate's blast radius, and the branch's own working tree carries an
  untracked `crates/apps/mainframe-env-server/examples/carddemo_signon.rs` that
  the gate now skips.
- **Spool append rollback can delete live data.**
  `crates/providers/mainframe-env-spool/src/service.rs:282` deletes the
  content-addressed chunk on a persist failure. Because the chunk digest covers
  job, file, sequence and records, an earlier successful append with identical
  values maps to the same artifact and would lose its payload. Narrow, but it
  silently drops committed spool data.
- **`edit_zoned` clobbers a digit for negative values.**
  `crates/apps/mainframe-env-batch/src/program.rs:671` does
  `edited.replace_range(..1, "-")`, overwriting the first character of the EDIT
  pattern rather than placing the sign ahead of the significant digits.
- **`JesQueue` is dead.** Defined at
  `crates/apps/mainframe-env-batch/src/jes.rs:167` and re-exported from
  `lib.rs:73`, but never referenced. Queue membership is derived from
  `JobState` instead.
- **Working-tree hygiene.** `screenlog.0` (a 52k-line agent session transcript
  including full command history) and the untracked `examples/` directory sit in
  the working tree, and neither is covered by `.gitignore`.

## Observations, not defects

- `install_mvs_tiot`
  (`crates/kernel/mainframe-env-interpreter/src/machine.rs`) keys the synthetic
  PSA/TCB/TIOT chain off sixteen exact COBOL data-item names. These are the
  conventional names for the TIOT-scan idiom and the status report is explicit
  about the bound, but it is still name-keyed compatibility behavior in kernel
  code: an equivalent program using different data names gets no TIOT. The
  de-hardcoding gate does not catch it because its forbidden list only covers
  CardDemo application identities.
- `VERSION` and `CHANGELOG.md` still read 0.7.0. That matches repository
  process — both are bumped in the separate `Release mainframe-env X.Y.Z`
  commit — and is not a branch defect.

## Effect on the frozen campaign candidate

Adding this file to the index changes the digest reported by
`cargo xtask jes-oracle-candidate`, because only
`conformance/0.8/evidence/jes-806-matrix.json` and
`docs/delivery/coverage-versions/status/0.8.0.md` are excluded from the
candidate domain. The frozen candidate
`sha256:2733803af3a110d6fc752d8ec9695f824ffc23f87554eaa026eb1fd3402bcd4d`
therefore describes the tree *before* this review was committed. Any licensed
z/OS 3.2/JES2 campaign must be re-pinned to the candidate that actually ships,
which the 0.17 CER-1702 gate requires anyway.
